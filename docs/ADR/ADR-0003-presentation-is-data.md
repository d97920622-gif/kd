# ADR-0003 -- Presentation is data: the string catalogue and the design tokens

- Status: Accepted
- Date: 2026-10-17
- Step: 1 (decided in sub-steps 1.3, 1.12 and 1.13, recorded in sub-step 1.32)
- Supersedes: none
- Superseded by: none

## Context

Two kinds of value in this application are written by a person and read by a
person, and both are normally scattered through the code that renders them: the
words, and the visual values. MASTER_PROMPT asks for the words to be centralized
in `lib/i18n/strings/en.ts` (line 34) and for "Tailwind CSS 3+ with custom design
tokens" (line 99), and the plan's segment gate for 1B is explicit: "no hardcoded
color or spacing value exists outside tokens"
(`docs/PLAN/08_SUBSTEP_CHECKLISTS.md`, segment 1B gate).

The reason is not tidiness. A colour that exists in fourteen files is fourteen
places to change and one place to forget, and dark mode is the demonstration: the
first component that hardcodes `#0f172a` is the component that shows a light
panel on a dark page. A sentence that exists in three components is a sentence
that says three things after the second edit, and it cannot be audited for a claim
the product is not allowed to make - which sub-step 1.28 turned into a rule
(a public page may not state a fact this build cannot evidence, enforced by
`check:public-site`).

So both kinds of value become data with one owner, and the code that renders them
reads them. The two differ in one way that matters: words need a key union that a
mistyped key fails against at compile time, and visual values need to be readable
by tools that are not TypeScript.

## Decision

**Interface copy lives in `lib/i18n/strings/en/`, one namespace per surface.**
`lib/i18n/strings/en.ts` aggregates the namespace modules; `t()` reads them; the
`EnglishStringKey` union is derived from the catalogue object, so a key that does
not exist is a type error in the editor rather than a blank space in the browser.
Keys are named for what they are (`meta_title`, `label_section_next_title`,
`action_features`), the catalogue nests no deeper than three levels, and the
protocol is **add, never rename**: a renamed key breaks every surface that reads
it, so a better word arrives as a new key and the old one is removed in the
sub-step that removes its last reader.

**The catalogue is enforced, not trusted.** `check:i18n-strings` walks the files
under `app/` and `components/` and refuses a literal string in JSX text or in a
display attribute (`aria-label`, `title`, `alt`, `placeholder`), so a control with
no visible text still carries an accessible name from the catalogue rather than a
word typed into the markup. The same check validates catalogue health: key naming,
duplicate keys across namespaces, non-empty ASCII values, placeholder shape
(`{name}`), and plural pairs that arrive as a pair.

**Visual values live in `config/design-tokens.ts`.** Spacing, radius, shadow,
z-index, typography, the colour roles with their contrast pairs, and the motion
durations are declared once as data with a comment per scale explaining what it is
for. `tailwind.config.ts` takes every scale from that module by identifier rather
than by repeating values, and `styles/globals.css` declares the CSS variables each
theme resolves. Four themes exist - light, dark, high contrast light, high
contrast dark - and a component that uses a role gets all four without a
conditional class.

**The token module is the only place a colour exists.** `check:design-tokens`
fails on an arbitrary Tailwind value (`p-[13px]`, `z-[9999]`), on a raw colour
literal, and on a raw inline style in an application file, and it verifies that
the mandated scales are present and that `tailwind.config.ts` reads them by
identifier. `check:color-contrast` compares `styles/globals.css` with
`config/design-tokens.ts` token by token so a theme cannot drift from the roles it
mirrors, and proves the pairs: 4.5:1 for text, 3:1 for focus and field boundaries,
7:1 in the two high contrast themes.

**Where a tool needs the values, they are generated.** `npm run tokens:export`
writes `config/design-tokens.json` from the TypeScript module and validates every
group; `npm run verify` runs it with `--check`, so the committed JSON is current
or the gate fails. The file is in `.prettierignore` and exempt from the path
comment rule because it is generated byte for byte, and the export check is what
proves it was not edited by hand.

## Consequences

- A palette change is one module and one regeneration; a theme that is missing a
  role is a finding, not a screenshot someone forgets to take.
- Copy is reviewable in one place, which is what let sub-step 1.28's claim floor
  and 1.29's page copy be audited at all: the checker reads the catalogue rather
  than the rendered page.
- Keys cost typing. `t('pricing.label_plan_notes')` is longer than a string
  literal, and the append protocol means a wording change adds a key and removes
  the old one in the same sub-step rather than editing in place.
- The four themes and the contrast ladder are a constraint on new colours: a
  role that looks right in three themes and fails in the fourth cannot ship,
  because the ratio check is part of the floor.
- Values that vary at runtime - a tenant's brand colour in white-label mode
  (step 11), an amount, a date - are data and never tokens. The token module is
  the vocabulary of the _application_, not a settings store.

## Alternatives considered

- **Inline values with a lint rule.** The lint rule (`no-restricted-syntax`)
  already refuses non-ASCII in literals; extending it to visual values would
  still leave no single place to change a scale, and no JSON export for tooling.
  Rejected.
- **A runtime i18n library** (`next-intl`, `react-i18next`). It brings message
  interpolation, plural rules and locale negotiation for a platform whose
  interface language is fixed by Rule 1 to English. The build needs a key union
  and a checker, not a locale runtime. Rejected for step 1; a later step that
  renders a tenant's own document language would revisit this record.
- **A JSON catalogue instead of TypeScript.** It would need a generated type to
  keep the key union, which is the same file count with one more build step and
  no compile-time check on the JSON. Rejected.
- **CSS-in-JS with theme objects.** One runtime, one theme object, and no
  Tailwind classes - which the mandated stack names. Rejected.
- **Semantic HTML with no copy layer.** Nothing to translate, and no way to audit
  a claim or keep a title and its description consistent across twelve pages.
  Rejected.

## Verification

- `check:i18n-strings` at this sub-step: 106 JSX files checked for literal copy,
  26 catalogue namespaces and 1022 keys validated.
- `check:design-tokens`: 248 source files scanned, 996 class lists checked, the
  spacing, radius, shadow, z-index, typography and motion scales verified as wired
  from `config/design-tokens.ts`, with reduced motion and forced colours verified.
- `check:color-contrast`: four themes, 23 colour roles, 76 ratios against WCAG
  2.1 AA, plus the paper palette's four tokens and three ratios.
- `npm run tokens:export` (with `--check`) proves `config/design-tokens.json` is
  the module's own output and is part of `npm run verify`.
- The 1B gate evidence records the components rendered in all four themes and
  under reduced motion in `app/(dev)/gallery/`, which reaches 404 outside
  development.
