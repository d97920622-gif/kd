## 2. The tenancy model these tables express

Three layers, and the `company_id` column says which layer a row belongs to:

1. **The tenant root** -- `companies`. `company_id` is null here _by design_
   and a named check enforces it: a tenant cannot be scoped to itself. The
   row's `id` is the scope every other table points at. Sub-step 2.7's policy
   for this table is therefore `id = current_company_id()`, not the usual
   column comparison.
2. **Platform-level identity** -- `user_profiles` and `platform_users`. A
   person exists across tenants, so `company_id` is null and a named check
   enforces it. Membership is what ties a person to a tenant.
3. **Tenant-scoped rows** -- `company_settings`, `company_members`,
   `invitations` carry a NOT NULL `company_id`. `devices` and `sessions` carry
   a _nullable_ `company_id` because a platform staff member acts outside any
   tenant; for every tenant member the column is set, and 2.7's policy scopes
   it.

Ownership boundaries this file deliberately does not cross:

- **`company_members.role` is the hierarchy level only** (`owner` or `staff`),
  matching `MASTER_PROMPT.md`'s five-role hierarchy. The permission presets
  (sales, accounts, support, manager, viewer -- FEATURE_LIST 602) and custom
  roles (603) belong to sub-step 2.4's `roles`, `permissions`,
  `role_permissions` and `user_roles`. Two dimensions, two owners, no second
  copy of the matrix.
- **`devices` and `sessions` store state only.** Revision 2 gives the device
  centre to 3.17 and the session registry, freeze and refresh rotation to
  3.18. These tables are their storage, the same way `login_lock_state` in
  2.4 will be the lock's storage with the flow in step 3.
- **`company_settings` holds the values later steps read** (timezone, fiscal
  year, session limits) -- the settings screen that edits them is step 4, and
  branding (FEATURE_LIST 558-573) is step 11.

## 3. Status columns are text with a named CHECK, not a native enum

The evolution policy (FEATURE_LIST K1, "enum versus lookup-table") is recorded
in the migration header:

- a closed set that changes only with a release uses `text` plus a named
  `chk_` constraint -- alterable in the same transaction that ships the
  change;
- a set that grows without a migration (plans, permissions, jurisdictions)
  uses a lookup table;
- if a native enum is ever introduced, it is named `{name}_enum` as
  `MASTER_PROMPT.md` requires.

A native enum would make `ALTER TYPE ... ADD VALUE` a migration of its own,
because the runner wraps each file in one transaction and a value added in
that transaction cannot be used by the same migration.

Three of these deserve a note:

- **`refused second active owner`** exercises the partial unique index
  `idx_company_members_company_id_owner` on `(company_id) WHERE role = 'owner'
AND status = 'active' AND deleted_at IS NULL`. The first version of the
  probe promoted the member without setting `status = 'active'`, so the index
  correctly did not fire; the corrected probe sets both and the index refuses.
  One active owner per tenant is enforced by the database, not by a service
  check.
- **`refused invited with a joined date`** is `chk_company_members_joined_at_
consistent`: an invitation that has not been accepted cannot carry a join
  date.
- **The three `delete` refusals are the `ON DELETE RESTRICT` rule** doing its
  job on a tenant, a person and a device.

The probe found no defect in the schema. Three probe bugs were fixed before
the run above and are recorded here so nobody re-learns them: the restore test
deleted the competing row after the restore instead of before, the owner test
omitted `status`, and one insert referenced `$1` without passing parameters.

## 9. What 2.3 deliberately leaves to its owners

- **RLS** arrives in 2.7, which enables a default-deny policy on every table
  and adds `check:rls-coverage`. Until then these eight tables are reachable
  by any role that can connect; the step gate records that 2.7 closed it.
- **Audit triggers** arrive in 2.8 for every table.
- **The auth link.** Step 3 adds the column that ties `user_profiles` to the
  auth provider's subject. It is not declared here, because a column no code
  reads is a placeholder and `MASTER_PROMPT.md` forbids one.
- **The reference-table foreign keys.** `companies.country_code` and
  `company_settings.currency_code` are format-checked text today; sub-step 2.6
  creates `countries` and `currencies` and adds `fk_` constraints in its own
  migration, because a foreign key cannot point at a table that does not exist
  yet.
- **Seed data.** The `super_admin` bootstrap profile is seeded in 2.14, not
  here; this sub-step creates no row.
