## 2. Design decisions

- **The claim is the identity.** Every policy reads the transaction-local
  setting `request.jwt.claims`, the JSON that PostgREST fills from a verified
  JWT. The keys are `sub`, `company_id` and `app_role`. An empty setting is an
  anonymous caller and matches nothing. A setting that is not JSON, or a
  `company_id` that is not a uuid, raises an error, so the database fails closed.
- **Default deny, forced.** A table with no policy for a role returns no rows and
  refuses every write. `FORCE` makes the table owner subject to the policies, so
  only a superuser or a `BYPASSRLS` role sees past them. The migration and seed
  runners need one of those in production; CI runs as the superuser.
- **Five shapes and no others.** Ledgers and login tables get `default_deny`
  (`USING (false)`) and no grant. The platform catalogue gets `shared_read` (an
  authenticated caller reads company-less rows) and `platform_write` (a
  `super_admin` writes company-less rows). A tenant table gets `tenant_isolation`.
  Devices and sessions get `own_rows`. User profiles and platform users get the
  self and colleague forms.
- **Membership is checked in the policy, not trusted from the claim.** A device or
  session may carry a company only while the user holds an active membership of
  that company. Company updates require an active owner membership, and the
  update may not move the row to another id.
- **No DELETE anywhere.** Rows leave by setting `deleted_at`, which keeps the
  audit trail whole. No migration grants DELETE, and the static check refuses one.
- **Companies are read and updated, never inserted by a tenant.** `companies`
  gets `SELECT` and `UPDATE` only; the platform creates a company.
- **The ledgers and login tables have no grant.** `schema_migrations`,
  `seed_migrations`, `login_attempts` and `login_lock_state` are closed to the
  application role entirely, so a later mistake in a policy cannot open them.
- **Tenant boundary, not permission matrix.** RLS isolates tenants. What a member
  may do inside its own tenant (a staff member inserting a role, for example) is
  the permission matrix's job in the application, sub-step 2.14 and step 3. The
  probe pins this boundary rather than assuming it.
- **The role survives the rollback.** `kd_app` is a cluster object. Dropping it
  fails when another database on the same server still grants it, so the down
  file revokes this database's usage and leaves the inert role (evidence
  section 5, defect 4).
- **The fuzz sweeps before it samples.** The first 156 rounds cover every tenant
  table, every operation and both attack directions once. Only the rounds after
  that are seeded random, so no table and operation pair depends on luck
  (section 5, defect 5).
- **Refusals are named.** A forged insert must fail with SQLSTATE `42501`, the
  policy's own refusal. Any other error is reported as a separate rule, so a
  constraint error can never pass for isolation.

## 5. Defects the loop found, and their fixes

Each defect is recorded because the loop caught it; none reached a commit.

1. **Helpers could not see each other.** The helpers were declared with
   `SET search_path = pg_catalog`, so `current_user_id()` could not find
   `current_jwt_claim()` in `public`. The migrate failed with `42883` and rolled
   back cleanly. Fix: the helpers call `public.current_jwt_claim`.
2. **A role with no grant broke the assertion.** The anonymous and per-tenant
   sweeps count rows in every table, and `login_attempts` has no grant to
   `kd_app`, so the count raised `42501` and the whole assertion failed. The
   refusal is the correct answer ("nothing visible"), so `rls_visible_count`
   turns `insufficient_privilege` into zero and re-raises every other error.
3. **Two probe expectations were wrong, and the policies were right.** The probe
   expected `42501` when a staff member inserted a role in its own tenant; the
   policy is tenant-scoped by design, so the insert succeeds. The probe also
   expected `42501` for an owner updating a global flag; row level security
   filters an `UPDATE` to visible rows and returns zero rows without an error.
   Both expectations were corrected, and the corrected probe pins the true
   behaviour (section 6).
4. **The rollback could not drop the shared role.** `DROP ROLE kd_app` was refused
   with `2BP01` while two other databases on the same server held grants to the
   role. The runner applies each file in its own transaction, so the policies
   were removed and committed before the framework file failed. The state stayed
   consistent but the rollback as a whole failed, and any developer with several
   databases would hit it. Fix: the down file revokes this database's usage and
   leaves the inert NOLOGIN role; the file header says how an operator drops it.
   The step 7 row above was re-run after the fix and passes.
5. **The fuzz sampled a pair it never reached.** The first draft drew each attack
   at random. A mutation that opened `DELETE` on invitations was not caught,
   because the 200 random draws never selected invitations with the delete
   operation. Fix: the first 156 rounds are a systematic sweep, every table, every
   operation, both directions. Coverage no longer depends on the random sequence.
6. **A DELETE policy alone widens nothing.** The first DELETE mutation opened
   only a `FOR DELETE` policy and expected a violation; none appeared, and
   direct checking showed `DELETE` affected zero rows. PostgreSQL requires the
   row to be visible to `SELECT` before `UPDATE` or `DELETE` can touch it, and a
   `FOR DELETE` policy grants no visibility. The original expectation was wrong,
   and the mutation suite now records both cases (section 6).
7. **A checksum guard refused an edited file.** A rollback against a database
   that had applied an earlier revision of the framework file was refused with
   checksum drift. That is the ledger working as designed: an applied file is
   never edited, so the database was rebuilt from scratch with the final files.
8. **Probe plumbing, not schema.** A seeded invitation reused a token hash across
   two tenants (the unique index refused it), a hash used a non-hex character (the
   check refused it), and a probe error left the client open so the process hung.
   Each was fixed in the probe; none touched the migrations.

## 6. Behaviour proof

**Probe: `rls-probe` against `kd_step27`, 50 assertions, PASS.** It runs as the
application role inside one transaction that is always rolled back, after seeding
two tenants, an owner and staff in tenant A, an owner in tenant B, a super_admin,
and the rows each table needs. It covers:

- positive controls: the owner reads its company, subscriptions, settings,
  devices, sessions, colleague profiles and the catalogue; it renames its company,
  updates its profile, inserts a role and files a device under its own company;
- refusals: staff cannot rename the company; no one moves a company to another
  id; no tenant writes another tenant's rows; no user files a device or session
  under a company it does not belong to; no user promotes itself to owner;
- the catalogue and flags: any authenticated caller reads the company-less plan
  and the global flag, and only a super_admin writes them;
- the ledgers and login tables refuse the application role with `42501`;
- no DELETE: a delete of a role is refused with `42501`;
- anonymous: no company, plan or flag is visible, and a write is refused;
- fail closed: a claim that is not JSON, and a company claim that is not a uuid,
  raise `22P02`.

**Mutation suite: `rls-mutation`, 9 of 9 PASS.** Each mutation is applied inside a
transaction, `rls_isolation_fuzz(200)` runs, and the transaction is rolled back.
The baseline must show zero violations, and each mutation must show the expected
rule.

| Mutation                                               | Violations reported                                                                    |
| ------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| baseline, no change                                    | none                                                                                   |
| subscriptions tenant policy opened to `USING (true)`   | cross-tenant read and write, forged insert, anonymous read                             |
| devices `WITH CHECK` opened                            | forged row accepted, cross-tenant write, forged insert refused by another rule         |
| `profile_colleague` opened                             | cross-user read on user_profiles, anonymous read                                       |
| companies read opened                                  | cross-tenant read on companies, anonymous read                                         |
| RLS disabled on roles                                  | cross-tenant read and write, forged insert, anonymous read                             |

After all nine mutations the companies table was empty again, so the rollbacks
left no row.

## 9. What 2.7 leaves to its owners

- **Sub-step 2.8** adds the audit ledger and its triggers. The `audit_logs` table
  is created with `default_deny` and no grant, as the ledgers are here, and
  written by a trigger that runs as the owner.
- **Step 3** binds the claims to the verified session. The database trusts whoever
  sets `request.jwt.claims`; the server sets it once per transaction from the
  session, and parameterised queries keep a request from setting it itself. Step
  15 audits that path.
- **Sub-step 2.14 and step 3** own the permission matrix: what a member may do
  inside its tenant (section 2).
- **Production runners** (migrate, seed, rollback) must connect as a role with
  `BYPASSRLS`, or as a superuser, because `FORCE` applies the policies to the
  table owner. The CI database job uses the superuser.
- **The live catalogue is the authority.** `check:rls-coverage` reads files so it
  runs in `verify` without a database. `db:assert` reads the catalogue in CI.
- **The companies table has no insert path for a tenant.** Creating a company is
  the platform's operation; its policy belongs to the step that owns company
  creation.
