Design decisions:

- **The ledger is the only source of applied state.** The file timestamp is the
  version; there is no second place a version is written.
- **The runner owns the transaction.** Each file runs inside `BEGIN ... COMMIT`
  together with its ledger row, so a failure cannot leave an applied table
  without its record, or a record without its table.
- **A checksum covers normalized text.** BOM removed, CRLF folded to LF,
  trailing blank lines removed. Any other byte change changes the hash.
- **One advisory lock** (`20260116000000`, the step 2 window start) serializes
  migrate, rollback and seed.
- **Rollback deletes the ledger row before running the down file**, inside the
  same transaction, because the framework rollback drops the ledger table.

## 5. `check:migration-pairs` could not see a pair

The check was written in sub-step 1.6 against an empty `migrations/` directory.
With the first real pair it reported four findings:

```text
migrations/20260116000000_migration_framework.sql:1:1: missing rollback file: migrations/20260116000000_migration_framework_down.sql
migrations/20260116000000_migration_framework_down.sql:1:1: missing rollback file: migrations/20260116000000_migration_framework_down_down.sql
```

Cause: the description group `([a-z0-9]+(?:_[a-z0-9]+)*)` is greedy, so
`_down.sql` was consumed as part of the description and the optional `(_down)?`
group never matched. Three defects followed from it:

1. the rollback file was classified as a forward migration;
2. both files claimed the same timestamp, which the check then reported as a
   duplicate;
3. `migrations/README.md` was reported as a badly named migration.

The fix strips `_down.sql` before matching, counts a timestamp only once per
pair, and skips non-SQL files. The corrected check then passed, and four
deliberate violations were proved to fail and removed:

```text
missing rollback file: migrations/20260116099999_probe_down.sql            (unpaired up file)
rollback file has no matching forward migration: migrations/20260116099999_probe.sql (unpaired down file)
timestamp 20260116000000 is already used by migrations/20260116000000_migration_framework.sql (duplicate)
migration name must match {14-digit-timestamp}_{snake_case_description}[_down].sql (bad name)
```

Final state:

```text
check:migration-pairs PASS (1 forward migrations paired with 1 rollback files)
```

This is the only step 1 file whose behaviour changed. It is recorded here
because the step 2 gate cannot be reported through a check that cannot see a
migration.

## 6. Two runners at once


The advisory lock serializes them: the second runner waited, then read the
ledger the first one committed. Neither reported a duplicate key and neither
applied the file twice.

## 8. CI

`.github/workflows/ci.yml` gained a `database` job, and the aggregate `ci` job
now depends on it. The job:

1. starts `postgres:16` as a service with a health check;
2. runs `npm ci`;
3. runs `npm run db:migrate` against the empty database;
4. runs `npm run db:rollback -- all` and `npm run db:migrate` again;
5. runs `npm run db:seed`.

The `DATABASE_URL` in the workflow points at that container only. It is not a
secret, it is not reused, and it is deleted with the runner.

## 9. Boundaries and what 2.1 does not cover

- **Row level security** is not enabled on the two ledgers yet. Sub-step 2.7
  owns the RLS framework and enables policies for every table in one place;
  enabling it here without policies would be a second owner.
- **`updated_at` triggers** arrive with `set_updated_at()` in 2.2.
- **`uuid_generate_v7()`** arrives in 2.2 and takes over the `id` default on
  both ledgers in the 2.2 migration.
- **Audit triggers** arrive in 2.8, which attaches them to every table.
- **Seed data** arrives in 2.14. This sub-step ships the runner and the
  contract; `db:seed` reports zero pending until the files exist.
- **No payment brand names, no AI, no test framework** were introduced.
