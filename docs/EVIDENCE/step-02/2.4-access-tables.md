## 2. The design decisions in this migration

**Roles are tenant rows; the permission catalog is platform reference data.**
`roles` carries a NOT NULL `company_id`: one tenant's "manager" is not
another tenant's. `permissions` carries a null `company_id` with a named check
that enforces it, the same shape as `user_profiles` in 2.3 and the reference
tables 2.6 will add: a catalog that every tenant reads and nobody owns.

**Two composite foreign keys enforce tenancy in the database.**

- `role_permissions (role_id, company_id) REFERENCES roles (id, company_id)`
- `user_roles (company_member_id, company_id) REFERENCES company_members (id, company_id)`
- `user_roles (role_id, company_id) REFERENCES roles (id, company_id)`

A composite foreign key needs a unique index on the referenced pair, so the
migration adds `idx_roles_id_company_id` and
`idx_company_members_id_company_id`. The second one has to be created before
`user_roles`; the first draft created it after and the migration failed with
`42830`, which is exactly the failure mode that makes the rule worth having:
the very first apply of a wrong order was refused, not silently skipped.

With these keys in place a grant can never straddle two tenants. Section 5
proves it with three distinct cross-tenant inserts, each refused with `23503`.

**`permissions.code` is the key and the parts must agree.** The check
`chk_permissions_code_matches_parts` requires `code = resource || '.' ||
action`, so a row cannot claim to be `invoices.delete` while carrying
`resource = invoices, action = update`. `category` is format-checked but not
enumerated: the resource list grows with later steps (payroll, expenses,
storage), which is the "lookup table" side of the enum-versus-lookup policy
recorded in the 2.3 header.

**`login_attempts` never stores an email in clear.** The column is
`email_hash` (SHA-256 hex, format-checked), plus a nullable `user_id` for the
resolved account. The same column becomes the blind index that 2.9 formalises,
and it is the one the velocity query reads. A successful attempt must have a
resolved account (`chk_login_attempts_known_account_on_success`), so the log
cannot record a success it cannot attribute. `correlation_id` is unique per
live row, so a retried handler cannot double-record one attempt.

**`login_lock_state` is storage only.** `failed_attempts`, `lock_level` (the
backoff stage), `first_failed_at`, `last_failed_at`, `locked_until` and
`lock_reason` are the state the step 3 flow will read and write. The
two-failure threshold, the 60-minute lock and the exponential backoff
(FEATURE_LIST 440, 441) are step 3, and no behaviour is implemented here. The
checks keep the state internally consistent: a lock needs a reason, a reason
needs a lock, the lock must expire after the last failure, and the first
failure cannot be later than the last.

**The permission override (FEATURE_LIST 606) is not here.** Step 4 owns the
matrix, its assertion gate and the screen; 2.4 creates the six tables the step
checklist names and leaves the override to its owner.

## 6. The lock state is durable across a server restart

The step 3 gate asks that the lock state survive a server restart. The storage
that gate depends on is this sub-step's, so the property was proven here:

```text
before restart: 1 held lock(s)
waiting for server to shut down.... done
--- server stopped ---
server restarted
after restart: attempts=2 level=1 reason=brute_force held=true
after restart: 2 login attempts retained
```

The server was stopped with `pg_ctl -m fast` and started again; the lock row
kept its counters, its backoff level, its reason and its `locked_until`, and
both login attempts survived. This proves the storage, not the step 3 flow:
the threshold and the backoff remain step 3's to implement.
