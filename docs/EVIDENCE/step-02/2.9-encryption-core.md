## 2. Design decisions

- **The root key is random bytes, not a passphrase.** A passphrase needs a
  password KDF (MASTER_PROMPT's PBKDF2 or Argon2id rule). A random 32-byte key
  needs only HKDF, which the vault uses. The decoder also refuses a spelling that
  does not re-encode to itself, so one key has one text form.
- **One derivation path.** Every key is HKDF-SHA256 of the root, with the salt
  `kd.encryption.v1` and the info `purpose=...;version=...`. The root is never
  used to encrypt directly, and a rotation is a new derivation, so the root
  stays untouched (FEATURE_LIST item 3188).
- **The envelope names its version.** `kdenc.v1.<purpose>.<version>.<iv>.<tag>.<ct>`.
  The version is in the clear, so a rotation can count and find the values that
  use an old version (FEATURE_LIST item 3190). Parsing rejects any text that does
  not re-encode to itself.
- **The associated data binds the header and the caller's context.** A value
  moved to another row, column, purpose or version does not open. Tests prove
  each of these (section 6).
- **A blind index is scoped and versioned.** It is HMAC-SHA256 over the
  normalised value (NFKC, trimmed, whitespace collapsed, lowercase), with a
  length-prefixed message that names the company and the field. The same value
  therefore produces no join across tenants or across fields. The stored form is
  `v<version>:<64 hex>`.
- **A field key is never a MAC oracle.** The vault's `mac()` refuses every purpose
  except `blind_index`.
- **Activation has two gates, and the inner one is the database's.** The function
  is revoked from PUBLIC and granted to `kd_app` only. Inside, it accepts a
  caller with `app_role = super_admin` in the session, or a session user who is a
  superuser or BYPASSRLS. It takes a per-purpose advisory lock, refuses a version
  that is not the next number, and retires the current version in the same
  transaction.
- **The ledger check closes the loop with the config.** The active version in
  `ENCRYPTION_CONFIG.activeVersions` must equal the database's, and every
  recorded key check must equal the one the environment root key derives. A
  deploy with the wrong root key fails here, before it writes a value.
- **Errors use the existing codes.** `ConfigurationError` (`configuration_error`)
  for a missing or malformed key and a bad rotation interval, and `InternalError`
  (`internal_error`, message never exposed) for an authentication failure or a
  bad envelope. `ValidationError` for an oversize field and a bad blind index
  input. No change to the error catalogue was needed.
- **No test files.** Rule 4 (`check:no-tests`) forbids them, so the rotation rules
  are a script, `encryption:rotation:rehearse`, that runs in verify and prints one
  line per case.
- **The logger is not changed.** `lib/logger/redaction.ts` remains the one rule
  set. `pii-redaction.ts` adds no rules; it only shapes what the encryption module
  may pass to a log.
- **The rotation interval is 90 days, and it is an owner decision.** MASTER_PROMPT
  layer 4 says 90 days. FEATURE_LIST item 3189 asks for annual rotation to be
  supported. The bound of 365 days supports annual use, and the default stays at
  the stricter 90 until the owner confirms it.
- **Key material and plaintext are never printed.** The root key is registered
  with the logger's secret registry when loaded, so a stray copy is masked. The
  scripts print an internal message that names the rule broken, never the value.

## 5. Defects the loop found, and their fixes

The work found these, and each was fixed before the result above was taken.

1. **The static check rejected the step-1 HMAC.** `check:encryption` first banned
   `createHmac` outside the vault. `lib/utils/hash.ts` uses it with a
   caller-supplied key, for a generic purpose, so the rule was too broad. The
   rule now covers only key derivation (HKDF), which is the path that matters.
2. **Lint order in the rehearsal.** Two parent imports were out of alphabetical
   order. Fixed with `eslint --fix`, and Prettier was run after it.
3. **A `pg` client typed as `any`.** `@types/pg` is not installed, so the client
   was implicitly `any` and a row parameter failed `strict`. The handler now
   names the `Db` type it uses.
4. **A configuration error hid its reason.** `runCommand` prints an AppError's
   public message, which for a configuration error is a generic sentence. The
   scripts now print the internal message, which names the rule broken and never
   the value. The output in section 6 shows the difference.
5. **A missing file was reported twice.** The check reported a missing file in
   both the reader and the main loop. The reader now only reads.
6. **CI refused to boot production.** The first CI run on the code commit
   (`f456c34`, run `39062029149`) was cancelled by the progress push that followed it,
   because the workflow cancels a run that a newer push supersedes. The run on
   `8458994` (run `39062115560`) then failed in the build job: its probe boots the
   production server, and `ENCRYPTION_KEY` is now required there. CI had no key.
   The cause was reproduced locally with `NODE_ENV=production npm run env:validate`,
   which named the missing key. The fix generates an ephemeral 32-byte key in the
   serve step and exports it only to the server. It is never written to a file, and
   the server log does not contain it. The local replica then passed both probes:
   `platform-probe.py` PASS and `http-hardening-probe.py` PASS.
   This is the rule working as designed: a production boot without the key fails.
7. **The rehearsal's blind-index case was shown to detect a regression.** A
   temporary edit that dropped the company from the blind index was made, and the
   rehearsal failed on that case with exit 1. The file was then restored. This
   shows the case is a real guard and not a check that passes by construction.

### 6.2 Rotation rehearsal, in memory

`npm run encryption:rotation:rehearse`: 8 of 8 cases PASS.

- The root key is accepted only as 32 random bytes in canonical base64. A
  passphrase, a 31-byte key and a non-canonical spelling of a valid key are refused.
- Fifty values written under version 1 open under version 2, re-encrypt to
  version 2 with the same plaintext, and a second pass changes nothing.
- A tampered ciphertext, a wrong context, a wrong purpose and a forged version
  header all fail to open. An oversize field and an oversize context are refused.
- The key check differs by version and by purpose, and matches for the same
  version under one root. The MAC is refused for the `field` purpose.
- The blind index is equal for two spellings of one value, and differs across
  companies and across fields. It carries version 1, and a rotated blind index
  carries version 2 with a different digest.
- Rotation is due at exactly 90 days, not at 89. An annual interval of 365 is not
  due at 90 days. An interval of 0 and of 400 are refused.
- 1234 rows give batches of 500, 500 and 234, which cover every row once.
- A log line for an envelope shows `kdenc.v1.field.2.[REDACTED]`, never the body.

## 9. What 2.9 leaves to its owners

- **Per-tenant data keys and their rotation window** are sub-step 2.10. This
  sub-step covers the platform keys only.
- **The re-encryption job for each table** that stores an encrypted field belongs
  to the step that introduces that table. 2.9 provides `reencryptEnvelope()` and
  `rotationBatches()`. No table in step 2 stores an encrypted field yet.
- **The rotation interval** is an owner decision (section 2). The default is 90
  days, and the bound of 365 supports annual use.
- **The production owner must hold BYPASSRLS.** The activation function is
  SECURITY DEFINER, as the 2.8 functions are. This is the same deployment risk
  recorded in the 2.8 evidence.
- **Backup of the root key** is the secret store's responsibility. Losing it makes
  every encrypted value unreadable, and the repository never holds it.
- **Root key rotation** has no procedure. FEATURE_LIST item 3188 says the root does
  not rotate.
- **Archiving retired versions** is not implemented. No version is deleted.
