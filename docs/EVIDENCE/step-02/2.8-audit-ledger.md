## 2. Design decisions

- **The chain covers content, and the signature covers the chain.** Each row's
  `current_hash` is SHA-256 over `previous_hash` and the canonical JSON of its
  content: sequence number, id, `created_at` in UTC with microseconds, company,
  user, action, resource type and id, the context fields, metadata and
  correlation id. The genesis `previous_hash` is 64 zeros. An Ed25519 signature
  covers the UTF-8 bytes of `current_hash`, so the signature is over the chain,
  not over each field separately. A changed row therefore fails the hash check
  first, and a changed hash fails the signature.
- **Sequence numbers are gapless under the lock.** `audit_logs_chain()` takes
  `pg_advisory_xact_lock(hashtext('audit_logs:chain'))` and writes
  `max(sequence_number) + 1`. Sequences do gap on rollback, so the lock is what
  keeps the number contiguous. The lock is separate from the deployment lock, so
  a migration cannot block the chain by accident. Every audited write in the
  database is serialised on this lock; that is a throughput cost, recorded in
  section 9.
- **The hash uses a fixed timestamp format.** `created_at` is hashed as
  `to_char(created_at AT TIME ZONE 'UTC', ...)`, never through the session's
  text output, so the hash does not depend on `TimeZone` or `DateStyle`.
- **Signature-only and `updated_at`-only changes are not audited.** The capture
  trigger skips an update whose only change is the signature or `updated_at`.
  Without this rule the signer would write a row for every row it signs, and the
  next run would never end.
- **Each checkpoint must cover at least one new row.** `audit_merkle_checkpoint()`
  writes a root only when a non-root ledger row exists at or after
  `first_sequence`. Otherwise it returns NULL. The first draft wrote a single-leaf
  root over the previous run's own audit row on every run; the guard stops that
  churn. Probe D5 pins the behaviour.
- **Signing is attach-once.** `audit_attach_signature()` and
  `audit_attach_root_signature()` update a row only while its `signature` is NULL,
  and nothing else can change a signed row (`audit_signed_once()`). Keys and
  roots are insert-only (`audit_append_only()` and the guards on each table).
- **Keys are registered once and never reused.** The signer refuses a key id
  already registered to a different public key, and it refuses an invalid key id,
  a non-Ed25519 key or a value that is not a PKCS#8 PEM. The private key is read
  from the environment only; the database holds the public key.
- **The verifier fails closed.** `db:audit:verify` runs the chain check too
  (added in this sub-step, after the first draft checked signatures alone). A
  content-only change therefore fails the verifier with `hash_mismatch`, even
  though its signature is still valid over the unchanged hash.
- **Read access follows the tenant.** `audit_logs` is FORCE RLS. A tenant reads
  its own company's rows. A `super_admin` reads the platform rows where
  `company_id` is NULL. The ledger takes no write policy, and no role but the
  definer functions can write.
- **Deviation from 2.7 shape, recorded here.** 2.7 gave no grant to `kd_app` on
  its tables. The ledger tables carry `GRANT SELECT` to `kd_app`, because the
  read policies above need it for a tenant to read its own trail. The grant is
  SELECT only. There is no INSERT, UPDATE, DELETE or TRUNCATE grant, and no
  DELETE policy. The rls coverage check reports 30 tables, 30 forced and 43
  policies, every policy `TO kd_app` alone, none open, no DELETE grant. The
  migration header names the policy shape `audit_read`; the policies themselves are
  `tenant_audit_read` and `platform_audit_read`.
- **Naming follows the universal standard.** `company_id` is the tenant column
  (MASTER_PROMPT says `tenant_id`), and `created_at` is the transaction
  timestamp (MASTER_PROMPT says `timestamp`). Both follow the rule that the
  universal standard wins over the field list.
- **`user_id` is not a foreign key.** An audit row must outlive the identity it
  names, so a deleted user does not take the trail with it. `company_id` is a
  RESTRICT foreign key, so a company with a trail cannot be removed.
- **The migration ledgers are audited too.** `schema_migrations` and
  `seed_migrations` carry capture triggers. The migration runner's own record of
  `070100` is therefore the first row of the signed chain.
- **`audit_logs` is exempt from capture.** A capture trigger on the ledger would
  write a row about every ledger row, and the chain would recurse. Its integrity
  rests on the chain, the signed-once guard and the truncate guard instead.
- **The down migration deletes the ledger.** `_down` drops the ledger, so a
  rollback of 2.8 in production is forbidden. The runner deletes the migration's
  ledger row first, inside the same transaction, and the deletion is itself
  captured while the capture triggers still exist. The audit tables are then
  dropped with that trail.

## 5. Defects the loop found, and their fixes

1. **Migration edited after it was applied.** The first build of `kd_step28`
   applied `070100`, and the file was then edited. The checksum drifted, so that
   database was discarded and rebuilt. Applied migrations are never edited. The
   rebuilt database passes the full loop above.
2. **Single-leaf root churn.** Each signer run wrote a Merkle root over the
   previous run's own audit row, so a no-change sign never settled. The checkpoint
   now writes only when a non-root row exists at or after `first_sequence`
   (section 2). Probe D5 confirms that a second checkpoint with no change writes
   nothing.
3. **Mixed failure message.** `db:audit:verify` listed unsigned rows and invalid
   signatures in one line. It now reports them on separate lines, and mentions
   unsigned rows only when some exist.
4. **Verifier did not check the chain.** A content-only change passed
   `db:audit:verify`, because the signature was still valid over the unchanged
   hash. The verifier now runs `audit_verify_chain()` too (section 6, tamper A).
5. **Probe defects, fixed before the audit probe ran.** The probe reused the
   name `root` for two values, which made the script fail to parse. It awaited
   inside a non-async callback. Its E2 check was a tautology, `count(...) LIMIT 0`.
   E2 now runs the real coverage SQL and expects an `audit_ledger_trigger_missing`
   row for `audit_signed_once()` when that guard is disabled.
6. **Probe URLs hard-coded to the 2.7 database.** `rls-mutation.cjs` and
   `violations-probe.cjs` had `kd_step27` written into the file, and ignored
   `PROBE_URL`. Early runs in this sub-step therefore executed against the 2.7
   schema, not the 2.8 one. The results cited in section 6 come from the corrected
   copies, `rls-mutation-28.cjs` and `violations-28.cjs`, run against fresh
   databases that hold the 2.8 migrations.
7. **Concurrency test draft.** The first draft searched metadata for company
   values, which the ledger never stores by design, and it indexed a row
   incorrectly. Both were fixed, and the final version asserts every condition.

## 6. Behaviour proof

Every run below is against a database built from the 2.8 migrations.

- **Audit probe, groups A to E, 61 of 61 passed.** A covers capture: inserts,
  updates, no-op updates, and the platform row. B covers `kd_app`: owner A sees
  only company A's rows, anonymous sees nothing, write, update, delete, truncate,
  signature attach, verifier, key register and checkpoint are all refused with
  `42501`, and the export is limited to visible rows. C covers immutability:
  update, delete and truncate of a ledger row are refused with `23001`, keys are
  insert-only, and a signature attaches once. D covers the checkpoint and an
  independent Merkle recomputation, which matches the SQL root. E covers tamper
  detection in rolled-back savepoints: a changed row is a `hash_mismatch`, a
  removed middle row is a `sequence_gap`, and a removed tail under a checkpoint
  gives `chain_truncated` and `merkle_leaf_count_mismatch`.
- **Documented limit, pinned by probe E4b.** A tail that no checkpoint covers
  leaves no trace in the chain, because no root yet covers it. The probe asserts
  that this is undetected, so the limit cannot change unnoticed. Section 9
  records it.
- **RLS probe, 50 passed, 0 failed.** Unchanged from 2.7, run against the 2.8
  schema.
- **RLS mutation probe, 9 of 9 detected, 0 residue.** Run as `rls-mutation-28.cjs`
  against `kd_mut28`. The unmodified probe, which hard-codes the 2.7 database,
  was not used for the 2.8 result.
- **Violations probe, platform probe and reference probe, all PASS.** Run against
  fresh databases. The reference probe reports 47 assertions.
- **Concurrency, four workers, PASS.** Four clients insert into `companies` at
  the same time, 30 rounds each, with every fifth round rolled back. That is 96
  committed inserts. The ledger ends with 97 rows: 96 `companies.created` rows
  and one `schema_migrations.created` row for `070100`. The sequence runs
  contiguously from 1 to 97, with no duplicates, and `audit_verify_chain()`
  reports zero violations. Every committed insert has exactly one row, and the
  rolled-back inserts left none.
- **Signer negative tests, all refused with exit 1.** A signing run with no key
  id; an invalid key id; a different key under a registered id; an RSA key; and an
  empty key. The
  verifier passed afterwards, so the refused runs wrote nothing.
- **Tamper tests on `kd_step28t` and `kd_step28t2`.** Both databases were
  signed, and both baselines passed `db:assert` and `db:audit:verify`. Each change
  was made as a superuser with `session_replication_role = replica`, which skips
  the triggers. This models a direct edit that bypasses the application.
  - **Tamper A, content only.** Sequence 4's metadata was changed. Its
    `current_hash` was left as it was. `db:assert` reports `hash_mismatch` on
    sequence 4 and exits 1. `db:audit:sign` refuses, with 1 chain violation, and
    exits 1. `db:audit:verify` fails with the same chain violation and exits 1.
  - **Tamper B, recomputed hash.** The same change was made, and the chain from
    sequence 4 onward was recomputed with `audit_entry_hash()`, so the chain is
    internally consistent. `db:audit:verify` reports six invalid signatures, on
    sequences 4 to 9, and exits 1. `db:assert` reports
    `merkle_root_mismatch` for sequences 1 to 8, because the signed root was
    computed over the old hashes, and exits 1. `db:audit:sign` refuses and exits 1.

## 9. What 2.8 leaves to its owners

- **Production owner role.** The audit functions are SECURITY DEFINER and read
  or write the ledger past its policies. That needs the owner to hold BYPASSRLS
  or be a superuser, the same requirement 2.7 places on the runners. If the owner
  lacks it, the chain sees no prior row and the unique index refuses the write,
  so the failure is closed. Nothing in the migration enforces the requirement.
  The deployment checklist must check it before the first production write.
- **Production signing key.** The sandbox used an ephemeral key. The production
  key is set in the deployment environment as `AUDIT_SIGNING_PRIVATE_KEY`, with a
  new `AUDIT_SIGNING_KEY_ID` for each rotation. The key lifecycle and rotation
  belong to the secret registry (2.11) and the rotation checklist.
- **Tail truncation window.** A tail that no checkpoint covers is not detected
  (probe E4b). The window closes at the next checkpoint. Checkpoint frequency is
  a deployment decision.
- **Rows before 2.8.** The ledger starts at the 2.8 deployment. Rows written
  before it are not chained. The database has no production data yet, so nothing
  is lost.
- **Throughput.** Every audited write takes the chain lock, so audited writes
  serialise across the database. That is the cost of a gapless sequence. A
  benchmark belongs with the encryption benchmark in 2.9 if the write rate grows.
- **Search and presentation.** The search and display of the audit trail are
  deferred to C1. This sub-step provides the rows and the export.
- **Rollback in production.** `_down` deletes the ledger. Rolling back 2.8 in
  production is forbidden.
